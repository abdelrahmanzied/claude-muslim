# Muslim pane — design

The Muslim pane's visual means and layout, following [DESIGN.md](../../../DESIGN.md). Behavior is in [muslim-pane.md](muslim-pane.md).

## Visual means

A Pane (`$.ui.open({ id: 'muslim', title: '☾ Muslim' })`) the only Muslim pane (there is no separate Quran pane), drawn by one Client (`client.tsx`) as an Svg holding HTML and CSS in a foreignObject, the approach every drawn mod card needs (the API has no HTML or native card element, so a drawn picture is the only way to match the Desktop's own session-panel cards: rounded bordered cards, a header with a chevron and a value, icon rows, a switch). `view.ts` builds the picture, `layout.ts` holds the fixed pixel layout and the hit testing, `model.ts` the pure data. Colors stay in `view.ts`: dark by default, light under the app's color scheme or the Claude theme row when it names light or dark, and the accent from `plugin/src/shared/color/` (the plugin-wide `/muslim color`, orange by default) for the next prayer, the next row, the switch, the progress bars and the play button. Fonts use the shared embedded Tajawal face described below; Arabic is left exactly as authored on desktop.

**Why a drawn picture:** the API has no native card element. **Fallback:** the terminal gets the unchanged status table from `/muslim` and a text body if the pane is placed there; Arabic goes through `plugin/src/shared/arabic`.

## Background and font

The pane draws no fill of its own: the root and the cards are `background:transparent` in both themes, so Claude Desktop's panel shows through; the cards keep only their 1px border line and rounded corners (the next-prayer row uses a transparent text overlay; only the play button, progress fills and enabled switches have solid accent fills). The type is Tajawal 400 and 700 for Arabic, Latin and numbers alike, embedded through `plugin/src/shared/font/` (shared with the Quran card's player; weight 500 resolves to 400). All text uses the fixed type scale in Layout below, without `.ar` font scaling; daily and settings cards share the same title size. Fixed heights and hit boxes stay aligned, with text centered by CSS. Prayer names and times, Athan, Quran metadata, the Athkar off note, and settings face/pill text use line-height 1 and a .12em downward shift to center Tajawal beside icons. The previous typography is preserved in git at `126e2bd`.

## Title row and folding

Every card shares one header (`.dh`, 28px at top 14): a 20px icon, the 16px title, a muted 12px value and the 26px fold chevron at the left end, 6px past the inset, in every card and both states. Prayer and Quran use the standard feature icons (`sujoodreal`, `qpane`); athkar uses the original athkar mark (`horizon`) for every set. Folded cards are 56px and the whole row unfolds. Folds live in session `muslim.paneFolds`; `cardRects` shifts every later card and target when a card folds or grows. All targets use the nearest-edge, half-cell slack arbitration.

## Light and dark

One token set per theme, switched by the app's scheme: dark by default, light under `prefers-color-scheme: light`. Claude Code's own `theme` row is not read (it can differ from the Desktop's, which made light mode draw with dark tokens). Elements take colors only from `VARS` in `view.ts`; raw hex and RGBA values stay in the palette CSS. There are no `--raised`, `--raised-2` or card-face fill tokens. The host remains visible through cards and controls.

Accent is reserved for play, the next prayer, progress fills, enabled switches and color dots; card-title icons retain their existing accent pending approval of neutral icons. Copy confirmation is neutral. No keyboard focus ring is drawn today, so this change adds none.

## Footer chip

On Desktop the footer's SessionMode row gets one plain Button, `☾ Muslim`, owned by this feature (its own `ui.render` hook, leftmost), followed by the prayer text and engine items (Quran adds no footer item). The label has a matching Text child and the button opens the Muslim pane when closed and closes it when open. It stays at every width. The SessionMode slot is the only footer space the API gives plugins and Desktop sets its width, so every item there stays short. Not drawn in the terminal. `paneButton` (default true) hides only this chip when off; it is changed from عام or `/config`, with `/muslim` as the entry point.

## Layout

A heading row, then three daily cards and one settings card stacked in one right-to-left column. The heading (`TOP_Y` 0, `TOP_H` 52px; the full avatar fills its height. The Desktop adds its own space above the picture and the API has no setting for it, so the heading starts at the picture's top edge; the 12px bottom margin is tuned against that space live): the full Muslim avatar, 52px tall and approximately 55.5px wide (`avatar.ts`, the still `claude-muslim` avatar from the claude-muslim-avatar repo (`assets/static/svg/claude-muslim.svg`): plain ivory kufi, short dark beard, closed smile, white thobe, nothing in its hands; pixelated, no background) and «مُسلِم» at 24px bold with a 10px gap at the right edge, 20px in; the LTR `/muslim` label at 12px dim at the left edge, 20px in, never hidden. Both «مُسلِم» and `/muslim` are vertically centered on the avatar row. It has no hit target. The cards start at `CARDS_TOP` (60px), 12px outside margin (`PAD` in `layout.ts`) and 12px between cards, 12px corner radius (the Claude Desktop side cards' radius; the next-prayer row inside uses 8px), 1px line border, 16px side padding, 28px header. Every height is a constant (the pane is CARDS_TOP + prayer + GAP + Quran + GAP + athkar + GAP + settings + PAD tall, see `layout.ts`), so the hooks module hit-tests clicks against the same numbers the Client draws with, whatever the data.

Scrolling moves the host's body window over this fixed picture only when there is actual overflow. A person-origin Desktop `ui.scroll` whose clamped offset equals the last rendered offset is consumed without drawing, including wheel/trackpad input over the passive reciter and surah labels and ticks at either edge. `UiScrollInput` has no surface field, so the hook remembers the pane's surface and offset from `ui.render`; it does not infer them from the session. Plugin-origin requests and the terminal text body pass through. The Client has no size polling: `ClientSurface` already calls it on resize, and polling a flickering measured row count only caused redundant `setState` picture swaps for size messages nobody used. Fixed SVG/card heights and the existing pointer mapping stay the same.

## States

- Hover lights a control or button with `--hover` (4% text overlay; the play button brightens); active setting choices use `--active` (7%). The pointer is whole cells on Desktop, so a target counts as hit when the cell overlaps it, the nearest one winning, as in the Quran pane. Each settings control (pills, switches, steppers, value and list buttons; not the tabs or the fold) also takes a press up to 2px left and right of its drawn edge (half the 4px gap to a neighbour) and 6px above and below (`CONTROL_SLOP`), so a press anywhere on the button, its padding included, counts even when the pointer lands a little off. The distance is still measured from the drawn edge, so a press inside one control always picks it, and a press between two picks the nearer.
- Inactive controls (no Quran catalog yet, first or last surah, segment repeat or «ابدأ من» on a whole surah, no city, athkar not ready) are dimmed and not hit.
- No scores or streaks: the athkar fraction is the person's own count, shown only to them.

## Full-player navigation

The Quran player lives in the card; there is no separate Quran pane: `/quran` with no arguments opens this pane at the Quran card, unfolding it if folded (a terminal gets a text status instead). Picks and repeat buttons go through the panel signal, so Muslim never imports Quran; Quran reconnects during the Muslim pane render and input chain. The scrollbar drag: the Client posts drag messages while a drag is in progress and the row scale is frozen at the press.

Values for other settings come from normalized options and Quran’s read-only feed, without a competing store.

The terminal gets all settings and their commands in tab order, عام first and the exact heading الذكر, through the existing Arabic `show` path. Native Desktop painting and scroll feel still require a live host check; engine tests prove geometry, input routing, state and API calls.

## Demo note

The final `pane` step of `/muslim demo` (or `/muslim demo pane` alone) draws the same card layout with a demo model: all cards folded, unfolding one by one and folding back, the settings card always folded. Nothing about the look changes for it; the timeline is in [the spec](muslim-pane.md#demo).

Quran failure expands the open player by 64px: one 20px dim 12px error line at `Q_ERROR_TOP` (286px plus the split offset), then a 30px «إعادة المحاولة» target at `Q_RETRY_TOP` (310px plus that offset), inset by the existing 16px sides. Text stays on one line; the button is full-width within those insets. `QuranLayout.error` drives both the added height and the retry rectangle in `layout.ts`; `hitAt` dispatches `quran-retry` through the shared panel channel. Folded cards keep their title-row height, and a picker sheet owns its pixels as before. The error clears on Retry, Stop, a new Play or selection change.

Athkar's «أكمل» is selected from positive repetition progress, including a partial first item, rather than the number of fully completed items. Method picks write the main settings face before config, restoring the methods face and toasting on denial or error. Every pane config writer awaits the shared stop-before-reload signal in DESIGN.md; Quran owns its single stop note.

Settings preflight the exact config row before optimistic changes or navigation, as specified in DESIGN.md. Missing rows keep the current face and playback intact and toast the shared reload-plugins message; a later missing-row error uses the same message and the existing rollback.

## Release behavior
